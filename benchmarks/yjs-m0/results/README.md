# M0 baseline results

These reports measure the required Grain baseline at commit `89d94625e12c0dd8e5db7728ad3a41de3445bc2d` with `yjs@13.6.33`. Fixture text and Grain IDs use seed `520052`. Yjs client IDs are generated by Yjs and recorded as observed values.

## Core profile

[core.json](./core.json) contains two fresh-process runs for all seven core fixtures. Each distribution has 25 warm-up and 200 measured operations. The JSON includes per-process p50/p95, dispersion, native operation counters, update and receipt bytes, checkpoint sizes, structures, ownership summaries, and heap/RSS observations.

The table reports the median across processes of each process's `prepareThroughPublish` p50 and p95. `p50 MAD` is the median absolute deviation across the two process p50 values. All times are milliseconds.

| Fixture                   |      p50 |      p95 | p50 MAD |
| ------------------------- | -------: | -------: | ------: |
| `paragraphs-10`           |    5.070 |    8.077 |   0.001 |
| `paragraphs-150`          |   46.622 |   81.298 |   0.081 |
| `paragraphs-1000`         |  391.553 |  679.387 |   3.906 |
| `paragraphs-5000`         | 2604.965 | 4382.348 |   6.237 |
| `long-tape-16384`         |    2.729 |    4.501 |   0.006 |
| `wide-list-1000`          |  524.875 |  839.684 |   0.024 |
| `fragmented-ownership-32` |   11.479 |   16.420 |   0.216 |

The wide-list structural move counter sample recorded 2,004 map sets, including 2,000 unchanged map sets; its accepted update was 50,611 bytes, receipt was 75,257 bytes, and checkpoint growth was 50,592 bytes. This is a single untimed counter sample, separate from the 200-operation timing distribution.

The original core timing distributions are retained. After instrumentation review, a two-process counters-only run refreshed the native count objects in `core.json`; the timed distributions, state snapshots, and memory observations were not rerun. Its exact command and environment are recorded in the report metadata. Delete-set counts now enumerate Yjs's `Map` values, and `publicDocTransactCalls` explicitly describes public method calls rather than native transaction lifecycles.

These are baseline observations from the runner, not portable performance claims. The proposal's engineering budgets apply to later implementation milestones.

## Browser profiles

Both browser reports use system Chromium `156.0.8078.73` at a `1280 × 720` viewport. Each profile has two fresh processes with 25 warm-up and 200 measured operations per process. The table reports the median across processes of each process's p50 and p95; `p50 MAD` describes the two process p50 values.

| Profile           | Report                         |       p50 |       p95 |  p50 MAD | Other observations                                          |
| ----------------- | ------------------------------ | --------: | --------: | -------: | ----------------------------------------------------------- |
| Editor            | [editor.json](./editor.json)   | 50.250 ms | 73.750 ms | 0.150 ms | 0 unaffected-block mutations; live block identity preserved |
| Full demo harness | [harness.json](./harness.json) | 58.400 ms | 86.950 ms | 0.800 ms | 200 parser rebuilds for 200 operations                      |

```sh
npm run bench:yjs-m0 -- --profile editor --runs 2 --output benchmarks/yjs-m0/results/editor.json --force
npm run bench:yjs-m0 -- --profile harness --runs 2 --output benchmarks/yjs-m0/results/harness.json
```

The editor report was refreshed after correcting the browser control: it resolves the affected and unaffected `md-block` elements by their `.node` identity and re-queries live DOM after all measured input has settled. Both live identities were retained in both fresh processes. The report uses system Chromium `156.0.8078.73` at `1280 × 720`.

The full harness measurement includes canonical change handling, Markdown and JSON serialization, parser rebuilds, and settled rendering. Browser timing is desktop Chromium simulation; it does not cover physical mobile input or IME behavior.

## Environment and command

The core report records the exact invocation and environment. It ran on Node.js `v26.13.0`, npm `12.2.1`, Linux x64 (`6.17.7-300.fc43.x86_64`), and an AMD Ryzen 9 5900X with 24 logical CPUs. This is not a pinned performance-worker result.

```sh
npm run bench:yjs-m0 -- --profile core --runs 2 --output benchmarks/yjs-m0/results/core.json
```

Ownership snapshots group tapes by `spanCount` and `ownerCount`, with `tapeCount` giving the number of tapes in each group. This preserves the ownership distribution without repeating fixture node IDs thousands of times. The report's timings and operation counts are unchanged by this compaction.

One instrumented process for the original M0 source completed the 0-, 64-, and 500-group measurements with 25 warm-up and 200 measured operations each. These single-process observations do not provide a repeated-process distribution. The process then recorded ten 100-action chunks in [retention-run-1.json.progress.jsonl](./retention-run-1.json.progress.jsonl). This original M0 trace remains incomplete and is not release evidence.

The trace reached 1,000 of 10,000 actions in 223.390 seconds. Its last 100 actions took 43.995 seconds. A quadratic extrapolation from the first 1,000 actions projected 6.21 hours for one trace and 18.62 hours for three fresh processes. Those values are planning estimates from the original M0 implementation, not completed measurements or estimates for later commits. The process stopped at action 1,000 under the runner's 120-minute limit. Keep this partial file as historical evidence; do not count it as a completed M0 trace or resume it as a measurement.

The separate R5 comparison against exact post-M5 commit `c3a8812e8bbee69c805a50347dd29d11c076d2de` completed three uninterrupted 10,000-action traces on each side. See the [R5 metrics and benchmark report](../../../docs/r5-metrics-and-benchmarks.md) and the [raw comparison artifacts](./r5-retention-post-m5-worker.json) with their [per-100-action progress log](./r5-retention-post-m5-worker.progress.jsonl). This completed the exact-post-M5 comparison gate. It does not replace or complete the separate original M0 trace recorded above.
